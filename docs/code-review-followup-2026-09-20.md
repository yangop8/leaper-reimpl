## 仍需修复的代码问题

### A. P2：预算仍是按范围的软上限，不是按块停止的上限

位置：[adapters/rocksdb/leaper_rocksdb.cc:235](../adapters/rocksdb/leaper_rocksdb.cc:235)。

SST 模式在范围开始前检查预算，但 238–245 行的内层扫描没有检查。一个范围可能覆盖整个文件，范围大小也没有代码层面的块数限制。因此预算不再无限扫全部范围，但仍可能在一个范围中超额很多。

重新编译当前 core 和 RocksDB adapter，以真实 SST 和公开 listener 回调验证：12,000 个键、每值 100 字节、无压缩、4 KiB 块，底层 LRU 缓存 64 MiB；单独设置适配器的预取预算。

```text
range=40000 keys; budget=32 blocks; actual counted=345 blocks, files=1, failed=0
range=1000 keys; budget=4 blocks; actual counted=31 blocks, files=1, failed=0
```

`actual counted` 是当前适配器的暖块统计口径。测试将底层缓存容量与适配器额度分开，避免缓存淘汰掩盖扫描是否停止。`range_size=40000` 也是适配器的常用默认范围规模。即使允许正常的少量读放大，当前超额幅度仍不是一个块级边界误差。

iterator 模式也只在 `Prefetch` 调用之间检查，单次 `warm_scan_keys` 扫描不受剩余额度约束，属于同一类粒度问题。

**建议：** 把剩余额度传入实际扫描函数，在内层读块过程中检查并及时停止；若有不可避免的单次读操作超额，明确限定其幅度。每任务独立预算的修改可以保留。

**影响边界：** 不否认此次修复有效，也不据此认定已提交的 3 GB 配置触发过预算。对大额度实验影响可能很小；但原报告要求的预算保护尚未完整实现，当前应描述为软预算。

### B. P2：一个 RocksDB 任务的 End 可以打断另一个任务的预测选择

位置：[adapters/rocksdb/leaper_rocksdb.cc:192](../adapters/rocksdb/leaper_rocksdb.cc:192)。

Begin 在适配器 `mu_` 内执行 `core.OnCompactionBegin → 多次 ShouldPrefetch`，以保证选择期间预测状态不被其他任务覆盖。End 却在释放该锁、完成预取后直接调用 `core.OnCompactionEnd`，没有获得同一把锁。

因此允许如下交错：

1. 任务 A 的 End 取出自己的待预取范围，释放适配器锁并完成预取。
2. 任务 B 的 Begin 获得适配器锁，设置 B 的核心预测状态。
3. A 在锁外调用核心 End，弹出上下文，恢复 B 开始前的状态。
4. B 继续执行 ShouldPrefetch，读取的是旧任务的状态。

核心自身的 mutex 只能保证每次调用不同时修改内存，不能保护整个 Begin→选择序列。基准设置了 `max_background_jobs=2`，任务并发不是未支持的场景。此处是当前代码的并发残留，与已经修好的共享预算计数器问题不同。

**受控复现：** 在当前适配器源码的临时副本中仅增加三个线程同步点，保留原锁和调用关系，强制上述合法交错。使用 WarmFlush 策略和 3 个候选范围，不需要真实 DB：串行时选择 3 个范围，交错时选择 0 个，预期应为 3 个。测试使用真实线程及重新编译的当前核心源码。WarmFlush 提供确定性反例；同一上下文恢复也会覆盖 learned 策略的热区。

**建议：** End 修改核心状态时也获取同一个适配器 `mu_`；无需把预取 I/O 一起放进锁内。也可以改为返回独立的每任务预测对象，但本次不需要为此大改接口。

**影响边界：** 这是有效执行顺序下的状态覆盖问题，不等于已证明它在某一条已存实验记录中发生，也不证明此次重测收益排序错误。

### C. README 的“四种策略中尾延迟最低”与新数据不符

位置：[README.md:189](../README.md:189)。

同一组 `m7fit_im_v4` 原始 CSV 中，按文档使用的每秒 read_p99_us 均值统计：

| 策略 | 每秒 p99 的均值（μs） |
|---|---:|
| stock | 28.420 |
| flush-only | 28.180 |
| Leaper SST | 36.415 |
| warm-all | 100.150 |

可以说 Leaper 比 warm-all 的尾延迟低，但不能说四种策略最低。这些是每秒分位数的均值，不是重建后的全程请求级 p99。

### D. “修复校准没有改变预测窗口，变化来自时间特征”缺乏依据

位置：[docs/M8-review-followup.md:1188](../docs/M8-review-followup.md:1188)。

旧 128 MB 校准应用到 3 GB 在线缓存时，三组旧记录的 k2 都为 1。按基准更新 QPS 的累计公式及 `ceil(T2/slot)` 从每秒 CSV 回算：

- v4 paper3：200 个时间点中 169 个对应 k2=2。
- v4 zipf09：199 个对应 k2=2。
- v4 fit_im：199 个对应 k2=2，1 个对应 k2=3。

这些是日志时间点的公式回算，不是捕获每次 compaction 的运行时步数；但足以说明“窗口没有改变”的解释不成立。T2 稍大于 1 秒就会因 ceil 变成两步，不能仅看校准报告取整后的 `1.0 s`。

两项修复同时应用后，不能把变化单独归因于 timestamp。建议改为“联合修复后的重测仍保持这些配置的策略排序”，这与实际结果相符。
